The decision everything follows from

Two planes, and an outbound-only boundary between them

v1 and v2 both drew this platform as a single stack. That is the omission that matters, because a buyer's first question is not what the agents do — it is where our credentials live and what leaves our subscription. The answer is the architecture.

What never crosses the boundary

  • Prompts and completions
  • Generated code and diffs
  • Tool arguments and results
  • Table, column and schema names
  • Any credential or secret
  • Any row of customer data

Tool arguments travel as SHA-256 digests, so we can see that two runs called the same tool the same way without seeing what they asked for. Payload export is opt-in per tenant, default off, and visible in the portal while it is on.

Inside the execution plane

Where the human sits, and what their approval is bound to

The seven steps are unchanged from v2. What v3 adds is the thing that makes the approval meaningful: a human approves a specific artifact digest, not a run. If the agent regenerates after approval, the deploy is refused.

Agent identity

One principal per agent, per tenant, per environment

"The agent runs as the platform service account" does not survive a security review: it grants every agent the union of all permissions and makes the audit log useless, because every action attributes to one identity. Instead:

The intersection rule

effective = agent_permissions ∩ invoking_user_permissions

An agent invoked by an analyst cannot write to a schema that analyst cannot write to, even where the agent's own principal could. Without this, invoking an agent becomes a privilege-escalation path — the classic confused deputy.

Principals are federated, so there is no secret to rotate or leak; tokens are scoped to a single run and expire in fifteen minutes. Destructive operations — DROP, TRUNCATE, force-push, merge — are not policy-gated, they are absent: no tool implements them.

How we will know it works

Acceptance rate, reported honestly

The metric is the percentage of agent outputs merged without human edit. It is always reported alongside median edit ratio and n, because a run "accepted" after a human rewrote half of it is not a success, and an 80% acceptance rate over five runs is noise.

The same telemetry tests the reuse thesis directly: runs that used a registry asset should show measurably higher acceptance than runs that did not. If that gap has not appeared by month three, the thesis is wrong and the roadmap changes. The comparison is built into the evaluation layer rather than left as an analysis someone might run.
